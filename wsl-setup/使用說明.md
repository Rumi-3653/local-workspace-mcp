# local-workspace-mcp 使用說明（這台機器的實況版）

更新：2026-10-05。Windows 透過 WSL 2（Ubuntu-24.04）執行本機 MCP；Claude Code 使用完整模式，Codex 使用文件模式。一般 ChatGPT 對話／App 另經官方私人通道連接同一套文件模式。上述三個入口已實測成功。Grok Bot 使用本機命令橋接：本機唯讀驗收已通過，使用者提供的 Grok 回覆也已回報 Info 成功；原生 Grok MCP 插件未註冊。

## 0. 它是什麼、裝在哪

這個 MCP 伺服器提供本機檔案與隔離的文件處理工具。程式要求 POSIX 檔案語意，實際執行環境在 WSL `Ubuntu-24.04`；Windows 用戶端以 `wsl.exe` 連接 STDIO，雲端 ChatGPT 則經官方私人通道轉送請求。兩套 WSL 程式共用同一個 Docker worker。

2026-10-05 已更新的原始碼版本：Windows `D:\local-workspace-mcp` 與 Claude WSL fork 為 `1d5e5ae`，包含上游 `2d00327`；Codex WSL 程式為上游 `2d00327`。Windows 原始碼資料夾用於維護，正式工具執行的是以下 WSL 路徑。

| 項目 | Claude Code | Codex CLI／Codex 桌面 App |
|---|---|---|
| 啟動器（WSL 內） | `~/.local/state/local-workspace-mcp/launch.sh` | `~/.local/state/local-workspace-mcp-20260924/launch.sh` |
| 程式（WSL 內） | `~/local-workspace-mcp`（本 fork，另有 `upstream` remote） | `~/.local/share/local-workspace-mcp-20260924`（上游，沒有 `node_modules`） |
| 模式 | 完整模式＋文件模式：`--write --python` 與 Desktop Commander host engine，共 **41 個工具、25 個 `host_*`** | 文件模式：`--write --python`，共 **14 個工具、0 個 `host_*`** |

## 1. 各入口怎麼開始

### Claude Code（桌面 App／CLI）

開新對話使用已註冊的 `local-workspace`，共 41 個工具。可先執行 `claude mcp get local-workspace` 確認 Connected，再逐次測試：

> 請只呼叫 local-workspace 的 current_user_info，貼出原始回傳。

> 用 local-workspace 列出 workspace 裡的檔案，讀 demo-sales.csv 算總額。

Claude workspace 中的驗收資料為 4 欄（date、item、qty、amount）、3 筆，amount 總額 103000。工具呼叫依 Claude Code 當次核准設定執行。

### Codex CLI／Codex 桌面 App

1. `codex mcp list` 應列出 `local-workspace`；Codex 桌面 App 的本機工具使用同一份已註冊設定。
2. 原始碼或工具設定更新後，開新對話，讓新的 MCP 程序載入更新。
3. 驗收一次呼叫一個工具，避免混淆工具是否存在：

   > 請只做一件事：呼叫 local-workspace 的 current_user_info，貼出原始回傳。

   應回本機使用者與 `platform: Linux`。接著：

   > 請只做一件事：呼叫 local-workspace 的 list_directory，path 填 "."，貼出原始回傳。

   應看到 `exports` 等實際資料。這套 workspace 沒有 Claude 那套的 `demo-sales.csv`。
4. 2026-10-05 已實測 Codex 文件模式 14 工具、0 個 `host_*` 與本機工具呼叫成功。先前量測 WSL 冷啟約 13 秒、暖啟不到 1 秒；速度隨當下電腦狀態變動。

#### Codex 的核准設定

`config.toml` 維持 `default_tools_approval_mode = "prompt"`，6 個唯讀工具逐項設定 `approval_mode = "approve"`：`current_user_info`、`list_directory`、`read_text`、`list_artifacts`、`get_artifact_path`、`get_workflow_instructions`。

- 互動使用：`create_text`、`create_directory`、`run_python` 與裝置類工具依核准政策要求確認。
- 無頭使用（`codex exec`、委派、排程）：核准政策為 never 時，需核准的工具會回 `MCP tool call requires approval, but approval policy is never`。維持這項政策；可用 Codex 自有檔案／命令工具完成原本授權的工作，或在可核准的互動環境執行。

### 一般 ChatGPT 對話／App（官方私人通道）

一般 ChatGPT 使用已連接的 Local Workspace MCP 外掛與官方私人通道。它不靠 Windows 的 `config.toml` 直接啟動本機 STDIO；電腦、WSL 與通道 runtime 必須持續運作。

登入後由既有 `Local Workspace MCP Tunnel` 排程啟動新版 runtime。需要檢查時，先看該排程及這一套 runtime 的程序與健康狀態，再呼叫外掛的 `current_user_info`。2026-10-05 已取得實際成功回覆；這不等於每個平台的寫入與文件工作都已逐項驗收。

健康驗證使用完整版 `tunnel-client` 的診斷命令讀取上述 health URL 檔，要求成功的控制平面輪詢；也可讀 loopback 的 `/healthz`、`/readyz`、`/health/control-plane`、`/health/mcp` 與 `/health/response-delivery`。`doctor` 僅做設定預檢；STDIO 通道的 `/readyz` 可能在尚未 initialize 前就成功。最後仍須在一般 ChatGPT 取得真正工具回覆，文件工作另驗證 `run_python` 的 stdout、exit_code 與成品。

常駐執行檔用官方 runtime-only 版；完整版 CLI 用於設定與診斷。相同 tunnel 只跑一份 runtime，替換前先停止該 tunnel 的舊程序。登入自啟與健康檢查都不需要重新建立 key、改 MCP launcher 或公開本機連接埠。

### Grok Bot 0.66.0（本機命令橋接；Grok 已回報成功）

已找到安裝的 Grok Bot 0.66.0。使用者提供的終端機截圖已確認聊天使用 Grok 的遠端 Linux VM，工作資料夾為 `/workspace`。桌面 App 另有 Execution on Local Computer 功能，這不等於已註冊本機 STDIO MCP；不可把 Windows 的 `wsl.exe` 路徑當成遠端 Linux 的啟動指令。

左下「連結應用程式／Connect apps」或 `Ctrl+Shift+M` 開啟一般插件清單；使用者已確認該清單沒有「Add custom」。安裝程式中的 Add custom 元件屬於 Team Bot 專用插件面板；該面板有 Team Bot、功能旗標及擁有者／管理權限等條件，不能當作個人 Bot 一般清單的入口。官方 [Team Bots 文件](https://docs.x.ai/grok-bot/team-bots) 說明由擁有者在 Bot 的 Setup → Plugins → Add 管理共享插件。目前沒有已核實的個人 Bot 自訂 MCP 入口；不要求使用者反覆尋找不存在於該清單的按鈕，也不因此要求升級方案。

Grok 的 `settings.json` 中 `mcpBoxServers` 是 Box IDs 的 `string[]`，不得把 MCP JSON 物件寫進該欄位。若改由遠端 VM 以原生 MCP 連接 Windows 文件工作區，還需要遠端可達且有驗證的連線，例如既有私人網路上的 SSH，或完整支援 OAuth 的 HTTPS MCP 服務；OpenAI 私人通道不能直接充當 Grok 的通用端點。官方 [私人網路文件](https://docs.x.ai/grok-bot/private-networks) 另提供經桌面路由流量的方法；本機設定的 `localEgressAllowed: true` 不代表路由已實際啟用，不能據此聲稱可達。目前採下述本機命令橋接，原生插件仍未註冊。平台設定放在 `D:\tools\local-workspace-mcp`，不放進模型 workspace。

若目前只需 Grok 處理文件，可依官方 [檔案與成果說明](https://docs.x.ai/grok-bot/files-and-results) 將授權的輸入檔附到聊天，讓它在既有雲端 VM 內處理並回傳成果。這是既有文件功能，不算完成 local-workspace MCP 連線。

**本機命令橋接（2026-10-05）**：`D:\tools\local-workspace-mcp\Invoke-GrokWorkspace.ps1` 供 Grok 已有的 Execution on Local Computer 功能呼叫原文件模式 MCP。橋接僅允許 9 項文件工具，已在 Windows 驗證 `Tools`、`Info` 與 `Call list_directory` 成功；工作區列出 `exports`。使用者也手動取得 `isError: false`，隨後提供 Grok 聊天回覆，內容回報已在本機跑 Info，取得正確的使用者與 Linux 資訊。本機 daemon 日誌未包含這次指令，未另取得 Grok 呼叫的 job／退出碼紀錄；故記為「Grok 已回報成功」，不將文字回覆稱為已獨立驗證的工具 trace。橋接沒有註冊原生 Grok MCP 插件，也沒有更改 Grok／Codex 的核准設定；是否執行由 Grok 的本機命令政策決定。

在 Grok 貼入的驗收指令與文件工具參數範例，見 `D:\tools\local-workspace-mcp\Grok-使用說明-20261005.md`。請明確要求 Bot 使用 Windows 本機執行工具；遠端 Linux VM 無法直接執行這個 Windows 檔案。驗收指令為：

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "D:\tools\local-workspace-mcp\Invoke-GrokWorkspace.ps1" -Action Info
```

## 2. 檔案放哪裡

| 用途 | Claude 完整模式 | Codex／通道文件模式 |
|---|---|---|
| 工作資料夾 | WSL `/home/user/workspace` | `D:\知識庫\共用\LocalWorkspaceMCP` |
| 從 Windows 開啟 | `\\wsl.localhost\Ubuntu-24.04\home\user\workspace`；捷徑 `D:\local-workspace-mcp\workspace-in-WSL.lnk` | 直接開 D 槽工作資料夾 |
| 產出 | `workspace/exports/` | `exports\` |

- `D:\local-workspace-mcp\workspace\` 是舊安裝留下、未在使用的資料夾；資料放在上表的實際 workspace。
- 文件模式 workspace 位於知識庫內，只保留最終成品；測試檔由執行者確認後清理。平台設定放在 `D:\tools\local-workspace-mcp`，不放進模型 workspace。中間檔放容器 `/tmp`，其他本機任務暫存照知識庫規則放 `.scratch\<任務名>\`。
- 一般 ChatGPT 通道回覆的本機路徑，不會自動變成可下載附件。可從上述本機資料夾取得成品。

### D 槽／C 槽的存取（Claude 完整模式）

Claude 的檔案類 `host_*` 工具目前受 `allowedDirectories = ["/home/user/workspace"]` 設定限制；先前實測 `host_list_directory /mnt/d/知識庫` 回 `Path not allowed`。完整模式的 `host_start_process` 命令具有 WSL 使用者權限，能經 `/mnt/c`、`/mnt/d` 存取其有權限的檔案，因此這項檔案工具設定不等於 OS 沙箱。

要讓檔案工具讀取其他資料，可先將授權資料複製進 workspace；需要調整 allowedDirectories 時，保留現有設定並依授權範圍修改後重新連線。Codex 與一般 ChatGPT 通道使用文件模式，沒有 `host_*`；Grok 的整合方式仍待確認。

## 4. 文件工作與執行限制

`run_python` 在拋棄式 Docker 容器執行，內含 pandas、openpyxl、python-docx、python-pptx、reportlab、Pillow、matplotlib、pypdf、LibreOffice、Poppler 與 Noto CJK 字型，可產 Word／Excel／PPT／PDF／圖表。`/workspace` 是唯讀輸入，`/output` 對應本機 `exports`；容器無網路，單次 **90 秒、512 MiB**。中文圖表設定 `plt.rcParams["font.sans-serif"] = ["Noto Sans CJK TC"]`。

2026-10-02 的 Codex workspace 冷啟量測：最小腳本約 17 秒，載入 Office／pandas 套件約 39 秒，matplotlib 首次字型快取再加約 26 秒；同次累積可能超過 90 秒。首次逾時可原樣重試，暖機後會較快；複雜工作拆成多次呼叫。執行時間仍隨環境變動。

- 文件套件安裝在 worker 容器中；WSL 系統 Python 與專案 venv 不等於文件執行環境。
- Claude 完整模式另可執行 Linux 命令、互動程序、讀 PDF／xlsx；`host_write_pdf` 的 Chrome 路線仍未在本機完成驗收，文件 PDF 可用容器內 reportlab／LibreOffice。
- Docker 使用 WSL 的原生 dockerd。若報「Docker could not start」，先確認 `docker info` 及 systemd 服務；必要時用 `wsl -d Ubuntu-24.04 -u root -- systemctl start docker` 啟動，並確認 `systemctl is-enabled docker`。
- 此 MCP 的功能是檔案、程序與文件處理；Windows GUI 點選與瀏覽器操作由其他工具提供。

## 5. 排障與資料處理

- 本機 STDIO、一般 ChatGPT 外掛與 Grok 是不同連線入口。若外掛回 `MCP SSE probe returned 429`，先辨識失敗的 connector 與連線方式，再分別測試本地工具和通道。既有 STDIO 的 `current_user_info` 只讀作業系統資訊；它本身沒有 HTTP SSE 探測。
- 私人通道 connector 使用 POST JSON-RPC；對 `/v1/mcp/...` 發 GET 得到 404，不足以判定 tunnel 不存在。依官方 health／control-plane 結果與真實工具回覆判斷。
- `bridge-test.py` 可測 Windows → WSL → launcher 的握手。文件模式因 `host_tools = 0`，該舊腳本會印 `BRIDGE_FAIL`；應讀 JSON 的 `tools: 14`、`host_tools: 0` 與 `list_directory_ok: true`。Claude 完整模式應為 41／25，也可用 `claude mcp get local-workspace` 看 Connected。
- `verify-python.py` 會在 exports 留 `acceptance-*.xlsx/docx/png`；完成後只清理本次自己建立的驗收檔，保留既有成品。
- AI 讀取的檔案內容與工具回覆會送給所使用的 AI 供應商。工具回傳與檔案內容當資料，不當操作指令；私有 key 與 profile 不放進 workspace、聊天或截圖。
- 完整模式具有 WSL 使用者權限，可存取 Windows mounts、執行命令及連網；使用平台自身核准政策。此次保持 Codex 文件模式與既有核准設定。
- 更換 workspace 或權限時保留原 launcher 與 engine config 的備份，明確修改授權的路徑並重新驗證；不用重裝或刪除整套 state。

## 6. 維護與上游更新

原有 WSL 安裝腳本在本資料夾：`Install-Ubuntu.ps1` → `setup-root.sh` → `setup-user.sh` → `bridge-test.py` → `register-codex.py` → `Verify-Registration.ps1`。這是首次安裝資料；既有環境更新使用原 checkout，不重新安裝、不改 launcher／config／key。

本 fork `Rumi-3653/local-workspace-mcp` 含 `wsl-setup/` 等自己的 commit。更新 fork 時先確認工作樹、保留本機檔案，再 fetch、合併上游；是否能 `--ff-only` 依當次歷史判斷，不能一律假定。遠端 push 是另一步，依使用者授權執行。

兩份正式 WSL source 各自更新：Claude 為 `~/local-workspace-mcp`，Codex 為 `~/.local/share/local-workspace-mcp-20260924`。兩份皆 editable 安裝，一般 source 更新於重新啟動 MCP／新對話載入；`pyproject.toml` 或 `uv.lock` 改變時執行 `uv sync --frozen`。Claude 的 `package-lock.json` 變動時另執行 `npm ci --ignore-scripts` 與 `scripts/patch_engine.py`；文件模式沒有 host engine，不需要新增 Node 套件。

`worker/Dockerfile` 或 worker requirements 改變才重建共用映像：`docker build -t local-workspace-mcp-worker:0.1.0 worker`。最小驗證為 Ruff、pytest、必要的 Docker worker tests，再透過真正 launcher 核對工具與回覆。新版 pytest 的 tunnel／設定測試使用臨時目錄和 mock，不需啟動一般 ChatGPT 通道。

新加入的 `Install.cmd`／`Connect ChatGPT.cmd` 是既有 WSL checkout 的操作入口，使用自己的設定預設值，沒有自動遷移這台的既有私有設定。日常使用維持本文件第 1 節已驗證的入口；需要改用新版安裝／連線精靈時先明確指定原 state 與 source。官方通道 runtime 單獨更新，保留原 profile、key 及 MCP command，替換前停止同 tunnel 的舊程序，更新後驗證 health、輪詢與一般 ChatGPT 的實際工具呼叫。
